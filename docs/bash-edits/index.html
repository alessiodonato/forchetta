In auto mode, more than a quarter of Claude Code's edits go through Bash

Your hooks don't see them.

22 November 2026. Numbers from my own transcripts; run the command at the end to get yours.

I build Forchetta, a Mac app that runs several Claude Code sessions in one folder. Its guard is a PreToolUse hook: when one session is changing src/api.ts in its turn, another session that tries to edit it is stopped, told why, and resumes when the file is free.

This week I measured how my sessions actually change files. The guard was blind to more than a quarter of the edits.

What changed

Since August, Claude Code's auto mode tells Claude to do much of its work through the Bash tool: read files with cat and sed -n, and make "small, mechanical file changes with sed, heredocs, or short scripts instead of the dedicated Read, Edit, or Write tools". People noticed:

  • #87971, Claude abuses bash tools for reads, writes, and edits when running in Auto Mode (103 👍, open)
  • #90450, Auto Mode's Bash-first instruction silently disables nested CLAUDE.md and path-scoped rules (51 👍, open)
  • #87575, Auto mode system prompt causes /rewind to silently fail on Bash-edited files (43 👍, open)

(Counts as of 22 November.)

Any tool that watches Edit|Write sees only part of the work. That includes file guards, format-on-edit hooks, review steps and audit logs.

The numbers

I counted the edits in my Claude Code transcripts of the last 30 days: 137 sessions, 82 of them in auto mode. I counted only files inside the folder each session ran in, outside .git and node_modules.

The shell commands were mostly here-documents (262: cat > src/config.ts <<'EOF'), then sed -i (158), then cp, mv and rm (54), plain redirects (41) and tee (3).

Two more groups I could not place, so they are not in the table:

  • 1,791 scripts write a file through a variable (open(path, 'w')), so the code doesn't say which file.
  • 1,390 commands can't be read without running them ($(…), subshells).

The true share outside the edit tools is somewhere above 27%.

By week, the edits outside the edit tools were 7% in the last week of October, then 43%, 34% and 26% in the three weeks after. The jump is mine, not Claude Code's: I started using auto mode in November. In October my sessions ran without it, and Claude made almost every edit with the edit tools.

This is one person's usage, and mine is heavy on scripted work, so your share will differ. That's why the command below exists.

What a hook can do about it

Read the command line. A PreToolUse hook on Bash gets the command before it runs. For most of these edits the line says which file is written:

  • the target of > and >>;
  • tee FILE;
  • sed -i '' 's/a/b/' FILE (and BSD's empty suffix);
  • perl -pi -e … FILE;
  • the destination of cp and mv;
  • what rm takes away.

Three details mattered more than I expected:

  • Here-documents first. Strip their bodies before parsing. A body is text for a program, and one apostrophe in it leaves a quote open, which makes the whole line unreadable. Mine became readable, and cat > f <<'EOF' turned out to be the most common form of all.
  • Quoted > is not a redirect. Track which > are outside quotes. grep '>' file writes nothing.
  • Count after, too. After the command succeeds (PostToolUse), treat the files it wrote as written by that session. Otherwise the next Edit from another session isn't stopped either.

Forchetta 0.12.3 does this. I wasn't first: agent-coord, a file guard for Claude Code, Codex and other agents, has read write targets from the command line since June, with the same two tricks for here-documents and quotes, and PowerShell's file cmdlets as well. In Forchetta, a sed -i on a file another session holds is now stopped like an Edit. The reason Claude reads says not to change the file "with an edit or with a command", so it doesn't route around the stop with Python.

What a line can't tell. A script that computes its path, find -exec, xargs, a formatter: the command line doesn't name the file. (Since 0.12.5 Forchetta knows the usual formatters, such as prettier --write and ruff format, and stops one that would rewrite a file another session holds. Which files it did rewrite, the line still doesn't tell.) Two ways to go further:

  • A sandbox per command. On macOS, sandbox-exec with a profile that denies writes to a single file stops redirects, sed -i and Python alike ("Operation not permitted"), with no root. Each launch took about 19 ms on my old MacBook Air. A hook could wrap each command with updatedInput. But a sandbox inside a sandbox fails: if you use Claude Code's own sandbox, this doesn't stack. And in auto mode Claude Code may refuse a call whose input a hook changed after review; the hooks documentation describes when. I haven't shipped this.
  • Compare before and after. Snapshot what changed in the working tree around each command and attribute it to the session. It's precise only when sessions don't run commands at the same time, which is exactly when you need it.
